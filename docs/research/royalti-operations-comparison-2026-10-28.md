## Build-versus-defer decision

**Retain and verify the existing server-owned ingestion/allocation pipeline. Do not commission a second importer or copy a competitor implementation.**

1. **Build next:** repair the observed FX default/1:1 behavior in the existing service and expose unavailable/stale data honestly to aggregation callers. This is a scoped correctness fix, not a new currency product or claim of settlement support.
2. **Verify next:** the real statement reimport exercise below, including owner isolation and held-state provenance. The existing code should satisfy this before adding more format breadth.
3. **Defer:** temporal/territorial/succession deal engines, automatic negative-obligation reversal, broad provider-template parity, white-label roster portals and automatic multicurrency payouts. Reconsider each only with a concrete required contract/provider case, authoritative data and an approved acceptance boundary.
4. **Keep separate:** CI-V3-20261021-03 owns recording/work exceptions; P-DDEX-20261022-01 owns receiver/schema compatibility; CI-V3-20261021-01 owns paid training permission. This comparison creates no duplicate GitHub issues or speculative ingestion build.

## Smallest prioritized acceptance exercise

This is a proposed test plan, **not an executed or passing customer-path test**.

1. Use `https://indii.music/` and an account genuinely created through the visible signup UI; record the actual plan and deployed revision. Stop for official email/MFA authorization when required.
2. Through the visible UI, import one statement genuinely belonging to that account, with a known provider, period, currency, fees, and owned catalog recording. Do not seed catalogs, inject sessions or alter entitlements to make the path pass. Record receipt ID, unmatched rows, gross/fee/net totals, held obligations and recoupment balance.
3. Reimport the same original bytes. Then, if the provider format supports it, upload a copy containing the same rows in a different order. The same logical receipt must not duplicate earnings, obligations or recoupment. Preserve duplicate legitimate rows as separate occurrences.
4. Use a second genuinely created account through normal sign-in. Its UI must not expose the first account's receipt, obligations or contact/payment details, and must not be able to change the first account's recoupment. No forged credentials or hostile requests against unrelated accounts.
5. Check reload persistence and evidence-linked agent answers. A missing quote, unmatched recording, negative adjustment or unapproved obligation must remain visibly unresolved. Do not initiate a transfer or claim a paid/registered result.
6. Treat concurrent retry and partial-write recovery as a separate controlled integration acceptance step; do not inject failures into a live customer's data. Preserve evidence and obtain an explicit safe environment before fault injection.
