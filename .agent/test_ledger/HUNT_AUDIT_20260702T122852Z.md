## Big Game Findings

### ISSUE-652 | OPEN | MEDIUM | Email Provider Mutations

- **Module:** Renderer / email providers
- **Evidence:** `packages/renderer/src/services/email/GmailProvider.ts:294-328` and `packages/renderer/src/services/email/OutlookProvider.ts:225-261` call Gmail/Graph mutation endpoints for `markAsRead`, `toggleStar`, and `trashMessage`, but never inspect `response.ok`.
- **Evidence:** `packages/renderer/src/services/email/EmailService.ts:317-339` exposes these methods as successful `Promise<void>` calls.
- **Evidence:** `packages/renderer/src/modules/agent/components/InboxTab.tsx:533-555` depends on rejection to revert star state or show trash failure, but HTTP 4xx/5xx responses from the providers currently resolve.
- **Impact:** Users can see messages marked read, starred, or trashed locally while the provider rejected the operation. The UI can show success for a failed destructive mail operation.
- **Fix Direction:** Capture each mutation response, read/log the error body, and throw on non-2xx statuses. Add focused provider tests for Gmail and Outlook mutation failure paths and an `InboxTab` optimistic-revert test for star/trash failures.
- **Verified?:** Static verified by source read; runtime provider calls not executed.

### ISSUE-653 | OPEN | LOW | E2E Mode Console Noise

- **Module:** Renderer / test harness mode guard
- **Evidence:** `packages/renderer/src/utils/e2eMode.ts:32-58` uses `console.log` in `isFirebaseE2EMockEnabled()` for normal disabled/enabled branches. The first branch logs on normal production calls when the runtime is neither a test harness nor local dev host.
- **Impact:** Production users can get repeated harness diagnostic logs in the browser console. It is low severity, but it violates the hunter workflow's raw-console rule and makes real console diagnostics noisier.
- **Fix Direction:** Replace branch `console.log` calls with the repo logger at debug level behind a dev/test guard, or remove the logs entirely. Keep warning/error reporting only for actual exceptional reads.
- **Verified?:** Static verified by source read; no runtime console capture performed.

### ISSUE-655 | OPEN | HIGH | Rights Credentials Used Directly In Renderer

- **Module:** Renderer / rights / PRO integrations
- **GitHub:** https://github.com/indii-music-founder/indii-music-founder/issues/214
- **Evidence:** `packages/renderer/src/services/rights/PRORightsService.ts:66-69` reads ASCAP API credentials from Firestore in the renderer and `:118-127` posts directly to `https://api.ascap.com/v1/works/register` with `Authorization: Bearer ${creds.apiKey}`.
- **Evidence:** `packages/renderer/src/services/rights/PRORightsService.ts:187-218` reads BMI username/password into the renderer and posts directly to `https://worksexpress.bmi.com/api/auth`; `:228-249` posts BMI work registration from the renderer.
- **Evidence:** `packages/renderer/src/services/rights/PRORightsService.ts:292-329` reads SoundExchange credentials into the renderer and posts directly to `https://api.soundexchange.com/v1/enrollments`.
- **Evidence:** `packages/renderer/src/services/rights/PRORightsService.ts:402-408` sends Music Reports API credentials from the renderer.
- **Impact:** Third-party rights credentials and tokens are exposed to browser/Electron renderer memory, devtools, and client network paths. This bypasses the backend-only API boundary used elsewhere in the app and makes CORS/provider behavior part of the user-facing control path.
- **Fix Direction:** Move ASCAP, BMI, SoundExchange, and Music Reports calls behind Firebase/Cloud Run functions that verify Firebase Auth/App Check, load provider credentials server-side, and return typed honest statuses. Renderer should submit only metadata and receive `registered`, `pending_credentials`, `manual_required`, or `failed` results.
- **Verified?:** Static verified by source read; provider calls were not executed.

### ISSUE-656 | OPEN | HIGH | PRO Setlist Submission Writes Fake Submitted State

- **Module:** Renderer / rights / live setlist submission
- **GitHub:** https://github.com/indii-music-founder/indii-music-founder/issues/215
- **Evidence:** `packages/renderer/src/services/rights/PRORightsService.ts:564-571` logs a PRO gateway submission and computes an ASCAP/BMI gateway URL, but never calls `fetch`.
- **Evidence:** `packages/renderer/src/services/rights/PRORightsService.ts:571-588` hardcodes `const mockResponseOk = true`, generates `SUB-${targetPRO}-...`, writes `submissionStatus: 'Submitted'` to Firestore, and returns `{ success: true }`.
- **Impact:** The app can tell an artist that an ASCAP/BMI live setlist was submitted when no external submission occurred. This directly affects royalty collection and business/legal trust.
- **Fix Direction:** Remove the fake success path. Either route setlist submission through a real secured backend integration or return an honest `manual_required` / `unavailable` result without updating Firestore to `Submitted`.
- **Verified?:** Static verified by source read; no live PRO submission attempted.

### ISSUE-657 | OPEN | HIGH | Royalty Report Ingestion Can Duplicate Payouts

- **Module:** Renderer / finance / royalty ingestion
- **GitHub:** https://github.com/indii-music-founder/indii-music-founder/issues/216
- **Evidence:** `packages/renderer/src/services/finance/RoyaltyService.ts:40-65` starts `ingestRevenueReport(reportId, ...)` and opens per-release transactions without checking whether the report was already processed.
- **Evidence:** `packages/renderer/src/services/finance/RoyaltyService.ts:82-103` deducts recoupment, calculates payouts, and writes each payout to `doc(collection(db, this.PAYOUTS_COLLECTION))`, generating fresh payout document IDs on every run.
- **Evidence:** `packages/renderer/src/services/finance/RoyaltyService.ts:108-113` writes the new recoupment balance, so duplicate ingestion can also mutate recoupment twice.
- **Evidence:** `packages/renderer/src/services/finance/RoyaltyService.test.ts:82-89` covers one successful ingestion only; no retry/idempotency regression is asserted.
- **Impact:** A user retry, importer retry, or duplicate upload of the same DSP report can create duplicate pending payout records and drift recoupment/accounting balances.
- **Fix Direction:** Add a processed-report claim or deterministic payout IDs based on `reportId`, source transaction, ISRC, and payee. Claim/check the report inside the transaction before creating payouts, and test duplicate ingestion plus partial retry behavior.
- **Verified?:** Static verified by source read; Firestore mutation was not executed.

### ISSUE-658 | OPEN | HIGH | Distributor Adapters Report Pending Review Without Confirmed Delivery

- **Module:** Renderer / distribution / distributor adapters
- **GitHub:** https://github.com/indii-music-founder/indii-music-founder/issues/217
- **Evidence:** `packages/renderer/src/services/distribution/adapters/TuneCoreAdapter.ts:87-139` attempts TuneCore API delivery, logs non-OK or fetch failure, then falls back to `success: true`, `status: 'pending_review'`, and a synthetic `TC-...` distributor release id.
- **Evidence:** `packages/renderer/src/services/distribution/adapters/BelieveAdapter.ts:122-173`, `OnerpmAdapter.ts:116-164`, and `UnitedMastersAdapter.ts:117-164` use the same success fallback after API failure or missing API delivery confirmation.
- **Evidence:** `packages/renderer/src/services/distribution/adapters/SymphonicAdapter.ts:73-101` returns `success: true` from the SFTP branch even if ERN generation, staging, or upload never ran because nested success checks were false.
- **Evidence:** `packages/renderer/src/services/distribution/adapters/DistributionAdapters.test.ts:68` mocks `fetch` to reject, while `:201-209` still expects TuneCore `createRelease()` to succeed as simulated API delivery.
- **Impact:** Artists can be told a release is in DSP review with a distributor release id when the app only generated ERN/manual-ready metadata or failed to contact the provider.
- **Fix Direction:** Reserve `success: true` for confirmed DSP API acceptance or SFTP upload. Return explicit `manual_required`, `delivery_unavailable`, or `ready_for_manual_submission` states for ERN-only/manual fallbacks, and update tests so rejected API calls do not pass as delivery success.
- **Verified?:** Static verified by source and test reads; no live distributor submission attempted.

## Small Game Findings

### ISSUE-654 | OPEN | MEDIUM | Workspace Snapshot Rehydrate Mutates Zustand State Directly

- **Module:** Renderer / workspace sync / Zustand store
- **Evidence:** `packages/renderer/src/hooks/useWorkspaceSync.ts:100-102` calls `applyWorkspaceSnapshot(snapshot)` after the user accepts a newer cloud snapshot.
- **Evidence:** `packages/renderer/src/core/store/index.ts:195-223` implements `applyWorkspaceSnapshot` by assigning directly to the object returned from `useStore.getState()` (`state.boardroomMessages = ...`, `state.currentModule = ...`, `state.notes = ...`, etc.).
- **Impact:** Direct mutation bypasses Zustand's `setState` notification path. The underlying object may change, but React subscribers, persistence middleware, and sync subscribers are not guaranteed to see a state update, so cross-device restore can silently fail or only partially update the UI.
- **Fix Direction:** Build a patch object and call `useStore.setState(patch, false)` for root-store fields; use the existing living-plan slice setters for plan state. Add a regression test that subscribes to `useStore`, calls `applyWorkspaceSnapshot`, and asserts subscribers are notified and selected fields update.
- **Verified?:** Static verified by source read; no runtime sync test executed.
